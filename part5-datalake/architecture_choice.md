## Architecture Recommendation

For a fast-growing food delivery startup collecting GPS logs, customer text reviews, payment transactions, and restaurant menu images, I would recommend a **Data Lakehouse** architecture.

A Data Lakehouse combines the raw storage flexibility of a Data Lake with the structured query performance and governance of a Data Warehouse — making it the most appropriate fit for this startup's highly diverse and rapidly growing data landscape. Here are three specific reasons:

**1. Multi-format, multi-modal data cannot fit in a Data Warehouse alone.** GPS location logs are high-frequency time-series streams. Customer text reviews are unstructured natural language. Restaurant menu images are binary blobs. Payment transactions are structured tabular records. A traditional Data Warehouse (e.g., Redshift, BigQuery in strict mode) is optimized for structured, schema-on-write data — it simply cannot store raw GPS streams, image files, or free-form text natively. A pure Data Lake could store all of these formats, but it lacks the ability to run reliable SQL analytics on them without significant additional tooling. A Lakehouse (e.g., Databricks Lakehouse, Delta Lake on AWS S3, or Apache Iceberg on GCP) handles all four data types in one unified platform: raw files land in object storage, while the transactional and structured layers are queryable via SQL engines with ACID guarantees.

**2. The startup needs both real-time and batch processing simultaneously.** Payment transactions and GPS logs demand near-real-time ingestion and processing (for fraud detection, live order tracking, and surge pricing). Customer reviews and menu images can be processed in batch (for sentiment analysis, recommendation engines, menu indexing). A Lakehouse with a streaming layer (e.g., Apache Kafka feeding into Delta Lake tables with Structured Streaming) handles both modes in the same platform — whereas a Data Warehouse struggles with streaming and a pure Data Lake lacks governance for reliable batch reporting.

**3. Schema evolution and agility at startup scale.** A food delivery startup's data model changes rapidly — new delivery zones, new payment methods, new review fields. A Data Warehouse enforces rigid schemas that require migrations for every change. A Data Lake has no schema enforcement at all, causing data quality degradation over time. A Lakehouse with Delta Lake or Apache Iceberg supports schema evolution natively: columns can be added without rewriting existing data, and time-travel queries allow auditing historical schema states. This gives the startup both the agility it needs to move fast and the reliability it needs to serve accurate analytics to business stakeholders.

A pure Data Warehouse would fail on unstructured data. A pure Data Lake would fail on query performance and governance. The Lakehouse is the principled middle ground.
