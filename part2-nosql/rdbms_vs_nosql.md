## Database Recommendation

For a healthcare startup building a patient management system, I would recommend **MySQL (or PostgreSQL)** as the primary database — with justification rooted in ACID compliance, the CAP theorem, and the fundamental nature of healthcare data.

Healthcare data is among the most sensitive and regulated data in existence. Patient records, diagnoses, prescriptions, and treatment histories must be accurate, consistent, and never partially written. This is precisely what ACID guarantees. Consider a real scenario: a doctor updates a patient's medication while simultaneously a nurse records a new allergy. These two writes must be fully isolated — a partial write could result in a patient receiving a drug they are allergic to. MySQL's strict ACID compliance prevents this class of error. MongoDB, by contrast, follows BASE semantics (Basically Available, Soft state, Eventually consistent), which explicitly tolerates temporary inconsistency across nodes. This trade-off is acceptable for a product catalog but is clinically dangerous for patient data.

From a CAP theorem perspective, when a network partition occurs (and in distributed systems, it will occur), MongoDB prioritizes Availability — it continues serving reads and writes, potentially returning stale data. MySQL prioritizes Consistency — it refuses to serve data it cannot guarantee is current. In healthcare, a doctor querying current medications must receive the actual current medications, not a cached version from before the last update. Stale data in a medical system is not a user experience problem; it is a patient safety problem.

Patient records also have a well-defined, stable schema: name, date of birth, diagnoses coded in ICD-10, vitals, medications, allergies, lab results. This structured, relational nature is exactly what RDBMS excels at. Relationships between entities (patient → prescription → drug → interaction) are enforced by foreign keys, not application logic.

**If a fraud detection module is required**, the answer evolves. Fraud detection in healthcare typically involves detecting anomalous billing patterns — a doctor billing for 300 appointments in one day, or duplicate claims across insurers. This requires high-throughput event streaming and graph-based relationship analysis (which patient IDs appear across which providers, payers, and pharmacies). The right architecture here is a **hybrid**: MySQL remains the source of truth for clinical records, while Apache Kafka streams billing events and a graph database (Neo4j) or columnar store (ClickHouse) powers the fraud analytics layer. The patient management core should not move to MongoDB — only the fraud detection pipeline sits alongside it with purpose-built tooling.
