## Vector DB Use Case

A traditional keyword-based search system would be wholly inadequate for the law firm's contract search system, and the reasons are fundamental rather than superficial.

Keyword search operates on exact or fuzzy string matching. If a lawyer queries "termination clauses," a keyword engine searches for documents containing those exact tokens. But a 500-page legal contract might use equivalent phrases like "conditions for dissolution," "grounds for rescission," "right to exit the agreement," or "circumstances under which either party may withdraw" — all semantically identical to "termination clauses," but lexically completely different. A keyword engine would miss every one of these occurrences, producing dangerously incomplete results in a domain where missing a single clause can have serious legal and financial consequences. Boolean keyword search also has no concept of relevance ranking based on meaning — it can only match strings, not understand intent.

This is precisely the problem vector databases are designed to solve. A vector database works by converting text into high-dimensional numerical embeddings generated by a language model (e.g., `all-MiniLM-L6-v2` or `text-embedding-ada-002`). These embeddings encode semantic meaning — passages with similar meaning are numerically close in vector space, regardless of the specific words used. The contract search system would work as follows: (1) each clause or paragraph in every contract is chunked and converted into an embedding vector at ingestion time; (2) when a lawyer asks "What are the termination clauses?", the query is also embedded; (3) the vector database performs an approximate nearest-neighbor search (e.g., using FAISS or HNSW indexing) and returns the most semantically similar passages, regardless of exact wording.

The vector database's role in this system is as the semantic retrieval layer — it bridges the gap between a lawyer's natural language intent and the precise legal language spread across hundreds of pages. A typical production architecture combines a vector store (e.g., Pinecone, Weaviate, or pgvector) with a large language model in a Retrieval-Augmented Generation (RAG) pipeline: the vector DB retrieves the top-k most relevant clauses, and the LLM synthesizes a coherent, cited answer from them. Without the vector database handling semantic retrieval, this system simply cannot work reliably — keyword search would fail on every paraphrase, every legal synonym, and every sentence that expresses the same clause in different words.
